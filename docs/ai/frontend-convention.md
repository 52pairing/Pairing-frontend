# Frontend Convention

React, Next.js, TypeScript, Tailwind CSS를 사용하는 프론트엔드 작업 규칙입니다.
코드를 작성하기 전에 현재 저장소의 코드, 폴더 구조, 컴포넌트, 스타일 패턴을 먼저 확인하고 기존 방식에 맞춥니다.

> 네이밍, 브랜치, 커밋 등 팀 공통 규칙은 루트 `README.md`를 따릅니다.

## 1. 기준 기술 스택

현재 프로젝트의 실제 `package.json`과 설정 파일을 기준으로 합니다.

- React 19
- Next.js 16 App Router
- TypeScript 5
- Tailwind CSS 4 (`@tailwindcss/postcss`)
- npm
- 경로 alias: `@/*` → `./src/*` (`tsconfig.json`)
- Lint: ESLint 9 + `eslint-config-next`
- 공통 API 클라이언트: 아직 미도입 — 도입 시 경로 기록 (확인 필요)
- 전역 상태관리: 아직 미도입 — 팀에서 확정한 방식만 사용 (확인 필요)

실제 프로젝트 설정과 이 문서가 다르면 실제 코드를 우선하고 이 문서를 갱신합니다.

## 2. 작업 전 확인

새 코드를 작성하기 전에 다음을 확인합니다.

1. 같은 기능 또는 유사한 화면이 이미 존재하는지
2. 재사용 가능한 공통 컴포넌트가 있는지
3. 기존 API 호출 방식이 무엇인지
4. 타입을 정의하는 기존 위치와 방식
5. 로딩·빈 상태·에러 처리 패턴
6. 반응형 및 접근성 처리 방식
7. 같은 도메인의 폴더와 파일 네이밍

기존 패턴이 있다면 새로운 구조를 만들지 않고 기존 방식을 따릅니다.

## 3. 폴더 구조

프로젝트의 실제 구조를 우선합니다.

현재 저장소에는 `src/app`과 `src/features`(비어 있음)만 존재하며, 아래는 프로젝트가 확장될 때의 권장 구조입니다.

```text
src/
├─ app/
├─ features/
│  ├─ auth/
│  ├─ client/
│  ├─ freelancer/
│  ├─ matching/
│  ├─ negotiation/
│  ├─ contract/
│  ├─ notification/
│  └─ common/
├─ components/
├─ hooks/
├─ lib/
├─ services/
├─ types/
└─ utils/
```

> 폴더명은 `src/features`(복수)로 통일합니다. `components`, `hooks` 등 모아두는 폴더와 동일하게 복수형을 사용합니다.

### `src/app/`

* 라우팅과 페이지를 관리합니다.
* Next.js App Router를 사용합니다.
* 페이지 컴포넌트에 복잡한 비즈니스 로직을 직접 작성하지 않습니다.
* 실제 기능 로직은 `src/features/`로 분리합니다.

### `src/features/<feature>/`

특정 도메인이나 기능에 속하는 코드를 모읍니다.

필요한 경우 다음 하위 폴더를 사용합니다.

```text
components/
hooks/
services/
types/
utils/
constants/
```

모든 기능에 위 폴더를 강제로 만들지 않습니다. 실제 필요한 폴더만 생성합니다.

### `src/components/`

여러 도메인에서 공통으로 사용하는 UI 컴포넌트를 둡니다.

특정 기능에서만 쓰는 컴포넌트는 해당 `src/features/<feature>/components/`에 둡니다.

### `src/lib/`

**인프라·설정 계층입니다.** 외부 라이브러리 연결과 저수준 공통 설정을 둡니다. 도메인 로직은 넣지 않습니다.

예시:

* API 클라이언트 인스턴스 (fetch/axios 래퍼)
* 인증 토큰·인터셉터 처리
* 쿠키 처리
* 외부 SDK 초기화 및 설정
* 공통 formatter, 상수

### `src/services/` 와 `features/<feature>/services/`

**API 호출 계층입니다.** `src/lib`의 API 클라이언트를 사용해 실제 요청 함수를 정의합니다.

* `src/services/`: **여러 feature가 공유하는** API 호출을 둡니다. (예: 공통 유저 정보, 알림 조회)
* `features/<feature>/services/`: **해당 도메인 전용** API 호출을 둡니다. (예: `features/matching/services`)
* 특정 도메인에서만 쓰는 API는 최상위 `services`가 아니라 해당 feature의 `services`에 둡니다.
* 컴포넌트에서 직접 `fetch`/`axios` 인스턴스를 만들지 않고 이 계층을 통해 호출합니다.

> 요약: `lib` = 클라이언트를 **만드는** 곳(인프라), `services` = 그 클라이언트로 실제 API를 **호출하는** 곳. 공통이면 `src/services`, 도메인 전용이면 `features/*/services`.

## 4. 컴포넌트 작성 규칙

* 기존 컴포넌트의 파일 분리 방식과 네이밍을 따릅니다.
* props는 TypeScript로 명확하게 정의합니다.
* 클라이언트 상태나 이벤트가 필요한 경우에만 `"use client"`를 사용합니다.
* 서버 컴포넌트로 처리할 수 있는 컴포넌트에 불필요하게 `"use client"`를 추가하지 않습니다.
* 한 컴포넌트에 화면 렌더링과 복잡한 비즈니스 로직을 모두 넣지 않습니다.
* 재사용 가능한 상태 로직은 커스텀 훅으로 분리합니다.
* 순수 계산과 변환은 `utils` 함수로 분리합니다.
* 하나의 파일이 지나치게 커지면 역할 단위로 분리합니다.
* 단순히 줄 수를 줄이기 위한 의미 없는 컴포넌트 분리는 하지 않습니다.

## 5. 상태 관리 규칙

* 작은 UI 상태는 해당 컴포넌트의 로컬 상태로 관리합니다.
* 부모와 자식이 함께 사용하는 상태는 props 또는 Context를 검토합니다.
* URL로 표현할 수 있는 필터·페이지·검색 조건은 URL 상태를 우선 검토합니다.
* 서버에서 가져온 데이터는 서버 데이터와 클라이언트 UI 상태를 구분합니다.
* Redux, Zustand, Recoil 등 새로운 전역 상태관리 라이브러리를 팀 합의 없이 추가하지 않습니다.
* 기존 상태 관리 방식이 있다면 같은 방식을 사용합니다.

## 6. 타입 작성 규칙

* `any` 사용을 피합니다.
* API 요청 타입과 응답 타입을 분리합니다.
* 화면 표시용 타입과 API 원본 타입이 다르면 변환 함수를 둡니다.
* 서버 enum 문자열을 임의로 변경하지 않습니다.
* 아직 확인하지 못한 필드는 추측해서 필수 타입으로 만들지 않습니다.
* 실제로 `null`이 내려올 수 있는 필드는 nullable 타입으로 명시합니다.
* 타입 단언(`as`)으로 오류를 숨기지 않습니다.

## 7. API 호출 규칙

* 프로젝트의 공통 API 클라이언트를 사용합니다.
* 컴포넌트에서 `fetch`나 `axios` 인스턴스를 임의로 새로 만들지 않습니다.
* 인증 토큰과 쿠키는 공통 인증 로직을 통해 처리합니다.
* API 호출 로직은 컴포넌트와 분리합니다.
* 요청 및 응답 타입을 명확하게 정의합니다.
* 백엔드 Swagger 또는 백엔드 PR의 변경 내용을 확인합니다.
* Swagger와 실제 응답이 다르면 실제 네트워크 응답을 기준으로 확인합니다.
* 프론트에서 실제 사용하는 엔드포인트는 `.ai/API.md`에 기록합니다.
* API 응답을 실제로 확인하지 못했다면 `.ai/STATE.md`에 미검증 사항을 남깁니다.

## 8. 폼 작성 규칙

* 입력값 검증 기준은 기획 또는 백엔드 정책과 맞춥니다.
* 프론트 검증만으로 보안을 보장하지 않습니다.
* 서버 검증 에러를 사용자에게 이해할 수 있는 형태로 표시합니다.
* 제출 중에는 중복 제출을 방지합니다.
* 입력 오류가 발생해도 사용자가 작성한 내용을 불필요하게 초기화하지 않습니다.
* 필수값과 선택값을 화면에서 명확히 구분합니다.
* 비밀번호, 계좌번호, 카드정보 등 민감한 값을 로그에 출력하지 않습니다.

## 9. 에러 처리 규칙

* 로딩, 성공, 빈 상태, 실패 상태를 구분합니다.
* API 실패를 무조건 빈 배열이나 `null`로 바꾸지 않습니다.
* 빈 데이터와 요청 실패를 같은 화면으로 처리하지 않습니다.
* 사용자에게 필요한 안내와 개발자가 확인할 로그를 구분합니다.
* 서버의 `errorCode`가 있다면 메시지 문자열보다 우선해서 분기합니다.
* 처리하지 못한 에러는 공통 에러 처리 방식을 따릅니다.
* 에러를 숨기기 위해 무분별하게 `try/catch`를 사용하지 않습니다.

## 10. Tailwind CSS 규칙

* 스타일은 Tailwind CSS 유틸리티 클래스를 사용합니다.
* 기존 색상, 간격, 타이포그래피, 버튼, 입력창 패턴을 우선 재사용합니다.
* 임의의 magic number보다 Tailwind 기본 스케일이나 프로젝트 토큰을 우선합니다.
* 반복되는 UI 패턴은 공통 컴포넌트로 분리합니다.
* 긴 `className` 조합이 반복되면 프로젝트의 기존 유틸 사용 여부를 확인합니다.
* styled-components, emotion 등 새로운 스타일 라이브러리를 팀 합의 없이 추가하지 않습니다.

## 11. 접근성과 사용성

* 버튼은 실제 `button` 요소를 우선 사용합니다.
* 입력 요소에 연결된 label 또는 접근 가능한 이름을 제공합니다.
* 키보드로 주요 기능을 사용할 수 있어야 합니다.
* 아이콘만 있는 버튼에는 의미를 전달하는 이름을 제공합니다.
* 로딩 중인지, 제출됐는지, 실패했는지 사용자가 알 수 있게 표시합니다.
* 클릭 가능한 요소와 비활성화된 요소를 시각적으로 구분합니다.

## 12. 금지 사항

* 기존 구조를 확인하지 않고 새 최상위 폴더 생성
* 동일 역할의 공통 컴포넌트 중복 생성
* 컴포넌트 내부에서 직접 토큰 처리
* API 응답 구조 임의 추측
* 팀 합의 없는 새 라이브러리 도입
* 타입 오류를 숨기기 위한 무분별한 `any`와 타입 단언
* 사용자 개인정보 또는 인증 정보를 콘솔에 출력
* 요청 범위 밖의 대규모 리팩터링

## 13. 확인이 필요한 항목

프로젝트 초기 설정이 확정되면 아래 내용을 실제 코드 기준으로 갱신합니다.

* 공통 API 클라이언트 경로
* import 정렬 규칙
* Formatter(Prettier 등) 도입 여부
* 폼 라이브러리
* 서버 상태 관리 방식
* 전역 상태 관리 방식
* 디자인 시스템 또는 공통 UI 경로
* 테스트 도구(Jest·Playwright) 도입 및 스크립트
