# 대주제 3. 구현 중 직면한 문제 & 해결 (2~3개만 깊게)

> 전부 쓰지 말고 **팀이 실제 겪은 문제 2~3개**만 골라 깊게. PM 파트에서는 특히 3-3(FE-BE 협업)이 말하기 좋음.

## 후보 문제 리스트 (여기 먼저 쌓고 나중에 2~3개 선정)
- [ ] 문제 A(협상): 배포 환경 실시간(STOMP) 전무 → ALB `/api/*` 라우팅 → `/api/ws` 한 줄로 해결 (BE-FE 협업·배포)
- [ ] 문제 B(협상): AI 대리인 동기 협상 10~20초(실측 16~17초) 무반응 → 로딩 UX(스피너+"10~20초 소요")로 체감 개선
- [ ] 문제 C(협상): 마지노선 초과 수락(`NG_011`) 막다른 길 → 그 자리에서 마지노선 수정 폼 자동 펼침
- [ ] 문제 D(협상): 조건 값 형식 불일치(한글 라벨·단위 누락 저장) → 타입별 입력 위젯으로 서버 형식 강제
- [ ] 문제 E(협상): A2A 비동기화 후 AI 실패 이벤트를 놓치면 화면 영구 정지 → `AGENT_RUNNING/FAILED` + `agentState` 폴링 폴백
- [ ] 문제 F(계약): HTML 계약서와 서버 PDF 이중 구현 시 조항 변경마다 동시 수정 → 서버 PDF Blob iframe으로 단일화

## 선정한 문제 1  _(후보 A — 협상 실시간 배포)_
- **상황(무엇이 문제였나)**: 로컬은 실시간 갱신이 되는데 **배포 환경에서는 협상 자동 갱신·채팅 실시간이 한 번도 동작 안 함**(항상 새로고침해야 보임)
- **원인**: 배포 ALB가 `/api/*` 경로만 백엔드로 라우팅 → `/ws` WebSocket 핸드셰이크가 백엔드에 못 닿고 프론트 404로 끝남
- **해결 과정**: BE-FE가 원인 추적(CORS 아님 → 라우팅 규칙) → 백엔드가 `/ws`·`/api/ws` 둘 다 열어두고, 프론트는 핸드셰이크 경로를 `/api/ws`로 **한 줄 변경**(로컬도 그대로 동작)
- **결과 / 배운 점**: 실시간이 살아남. "실시간이 안 되는 건 프론트 버그가 아니라 인프라(경로/프록시) 문제일 수 있다"는 협업 교훈
- **근거(커밋·PR·캡처·수치)**: `src/features/negotiation/stomp/client.ts` `resolveBrokerUrl()`, 브랜치 `fix/common-negotiation#79`

## 선정한 문제 2
- **상황**: A2A 협상이 비동기로 바뀌며 제출 API는 즉시 응답하고 AI 처리는 약 15초 뒤 완료. AI 호출 실패 시 라운드가 오르지 않고 기존 완료 이벤트도 오지 않아 화면이 "대리인이 협상 중"에 영구 정지
- **원인**: 프론트 이벤트 타입·분기에 `AGENT_RUNNING`/`AGENT_FAILED`가 없었고, WebSocket이 1006으로 끊기면 상태를 복구할 폴링도 없었음
- **해결 과정**: 두 이벤트 타입과 상세·메시지 재조회 추가 → `agentState`를 화면 문구 최우선으로 적용 → RUNNING 동안 2.5초 GET 폴링 → 이벤트 도착/상태 종료 시 자동 중단 → FAILED에서 SYSTEM 안내와 동일 마지노선 재시도 제공
- **결과 / 배운 점**: 🎤 실시간 이벤트만 믿지 않고 **STOMP 즉시성 + REST 폴링 복구력**을 결합. 성공 흐름뿐 아니라 "AI가 실패했을 때 사용자가 다시 행동할 수 있는가"까지 제품 흐름으로 설계
- **근거**: Issue #119, `fix/common-negotiation#119`, `NegotiationRoom.tsx`, `NegotiationChatFlow.tsx`, 실서버 `CONNECTED / heart-beat:10000,10000 / user-name` 확인

## 선정한 문제 3
- **상황**: 프론트 HTML 계약서와 백엔드 PDF가 별도로 존재해 AI 주요 업무 추가·동적 조항 번호·계약 금액·근무 장소 정책이 바뀔 때 양쪽 수정 필요
- **원인**: 동일한 계약 문서를 프론트와 서버가 각각 렌더링해 표현의 단일 출처가 없었음
- **해결 과정**: 서명 화면 본문을 서버 PDF Blob iframe으로 전환하고 전자서명 UI만 프론트에 유지. 대금 분할·수정하기처럼 API나 정책이 없는 시안 요소 제거
- **결과 / 배운 점**: 🎤 서버 PDF를 계약 문서의 단일 출처로 정해 정책 변경 누락과 이중 유지보수 위험 감소. 화면 구현량보다 **변경 비용과 데이터 책임 경계**를 우선한 의사결정
- **근거**: Issue #92, `ContractDocument.tsx`, `GET /api/v1/contracts/{contractId}/pdf`, PDF Blob/iframe 화면 캡처

### 3-3. FE-BE 협업 문제 메모함 (PM이 말하기 좋은 소재)
> 아래는 "떠오르면 적어두는" 체크리스트. 해당되는 것만 메모.
- API 계약 합의 (스펙 확정 시점·주체, 변경 통보 절차, 불일치로 인한 재작업):
  - 📌 협상/채팅 실시간은 Swagger에 안 뜸(STOMP over WebSocket) → 백엔드가 별도 md 계약 문서로 전달, `docs/api/negotiation-*.md`에 보관
  - 🎤 계약이 **여러 차례 반복 변경**되며 프론트 재작업: 필드명 `title→projectTitle`, 조건 `conditionType→type`(요청 바디만 conditionType 유지), `negotiationNo` number→string
  - 🎤 값 형식 불일치로 **DB 저장이 깨짐**: 프론트가 `"재택"`(한글)·단위없는 `"4"`를 전송 → 백엔드가 형식검증(`NG_004`) 추가 예고 → 프론트를 **조건 타입별 입력 위젯**(만원→원 ×10,000 / `"4 MONTH"` / enum 코드 `REMOTE`·혼합=`ANY`)으로 수정
- 화면 단위 데이터 책임 (서버 조립 vs FE 조합, 화면 전용 API 판단):
  - 📌 "초기=REST(GET) · 이후=STOMP 실시간" 짝으로 역할 분담
  - 🎤 카드 빨간점 데이터가 협상 API가 아니라 **매칭 API(`newProposalCount`)** 에 있어 두 도메인 합쳐 렌더 (책임 경계 조율)
- 도메인 용어·상태 기준 정렬 (같은 대상 다른 명칭, 상태값 정의 불일치 예: 완료/종료/마감):
  - 🎤 같은 `REJECTED` 상태를 "재협상"/"재입력 필요" 두 이름으로 부름 → **"재협상 필요"로 통일**(서버 라벨 기준)
  - 🎤 "대리인이 협상 중" 문구가 실제와 불일치(거절은 라운드 안 돎) → `waitingForMe`+`REJECTED`로 상태 문구 재정렬
  - 📌 헤더 종 배지 vs 버튼 빨간점 혼선 → 소스 구분(`waiting-count` vs `newProposalCount`)
- 통신·에러 처리 설계 (에러 코드 체계, 사용자 노출 메시지 책임 FE/BE):
  - 🎤 백엔드 에러코드를 UX로 연결: **`NG_011`(마지노선 초과)** → 오류만 띄우지 않고 **그 조건 수정 폼 자동 펼침**(막다른 길 제거). `NG_004`(형식)·`NG_006`(합의 조건 수정불가)·`NG_003`(중복 제출)도 각각 처리
- 통합 검증 환경 (mock 데이터, 테스트 계정, 로컬 vs 개발 환경 차이):
  - ❓ 검증에 로그인 쿠키 + `NEGOTIATING` 실데이터 필요 → 테스트 데이터 부족으로 검증 지연
  - 📌 AI 서버 폴백 시 메시지에 `(stub)` 저장(프론트 문제 아님) → 원인 구분에 시간
  - 📌 로컬(localhost:17000) → 배포 백엔드 CORS 이미 열려 있어 로컬에서 실서버 테스트 가능
- 배포·운영 (FE/BE 동시 반영, 환경변수 관리, 배포 후 확인 절차):
  - 🎤 **배포 환경 실시간이 한 번도 안 됨** → 원인: ALB가 `/api/*` 만 백엔드로 라우팅 → WebSocket 경로 `/ws`→**`/api/ws`** 한 줄 수정으로 해결
  - 📌 WS도 쿠키 인증 → 배포 시 `CORS_ALLOWED_ORIGINS`에 프론트 도메인 등록 필요(REST+WS 공용)
  - 🎤 비동기 A2A 배포 후 실서버에서 `CONNECTED`, 사용자 식별, 하트비트 `10000,10000`, `AGENT_RUNNING→AGREED` 실시간 흐름까지 검증. 단, 검증 중 1006 연결 종료를 경험해 REST 폴링 폴백 필요성을 실제 장애로 확인

- 계약·정산 API 책임 경계:
  - 🎤 계약 상세는 단일 API 응답, 계약 문서 본문은 서버 PDF를 단일 출처로 확정 → FE는 상태·서명 인터랙션에 집중
  - 📌 계약 상태와 결제 가능 여부를 조합해 버튼 분기(`SIGN_PENDING` 서명, `SIGNED` 착수금, `COMPLETION_PENDING` 성공보수). 상태 하나만 보고 판정했을 때 버튼 누락·잘못된 서명 대기 표시 발생
  - 🎤 정산 완료 화면은 프로젝트·계약 API를 여러 번 조합하지 않고 `/settlements/mine?projectId=` 한 번으로 착수·성공보수 내역 구성. 전체 수수료만 FE 합산해 서버 책임과 화면 계산 범위를 명확히 함

**기록**
- 🎤 협상 도메인은 "실시간 + AI 대리인 + 사람 승인"이 얽혀 **FE-BE 계약 조율이 가장 많았던 파트** — 계약 문서 왕복·용어 정렬·에러 UX·배포 라우팅까지 PM 협업 소재 집약

> 위에서 쌓인 재료 중 "이건 발표 흐름에 이렇게 쓰자" 아이디어를 여기 모음.

- 🎤 에러를 막다른 길로 두지 않기: `NG_011`(마지노선 초과) → 그 자리 수정 폼 자동 펼침. "사용자가 다음에 뭘 할지 모르게 두지 않는다"는 UX 원칙
