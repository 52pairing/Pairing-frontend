# 1. 불필요한 리렌더링 추적과 제거

## 1-1. 개념 (왜 문제인가)
- React는 부모가 리렌더되면 **자식도 기본적으로 다 리렌더**된다. state가 새 객체/배열 identity로 바뀌면 그 트리 전체가 다시 그려진다.
- 화면 결과가 같아도 **reconciliation 비용**은 발생한다. 리스트가 길거나 주기적 갱신이 있으면 체감 렉·발열·배터리로 이어진다.
- 방어 도구: `React.memo`(props 안 바뀌면 스킵), `useMemo`(값 캐시), `useCallback`(함수 identity 고정). **단, 무지성 남발은 오히려 손해** — 병목을 측정으로 확인한 뒤 적용.

## 1-2. 우리 프로젝트 사례 (확정)
- **협상룸 폴링 재렌더 폭탄**: [NegotiationRoom.tsx:197-205](src/features/negotiation/components/NegotiationRoom.tsx)가 **2.5초(AI 협상 중)/10초** 간격으로 `refreshDetail()`+`refreshMessages()` 호출 → `setDetail`/`setMessages`가 매번 **새 객체 identity** 생성 → 자식인 **1233줄 [NegotiationChatFlow.tsx](src/features/negotiation/components/NegotiationChatFlow.tsx) 전체가 매 폴링마다 재렌더**.
- 자식 컴포넌트(`MessageItem`, `NegotiationHeader`, 패널들)에 **`React.memo` 없음** → 메시지 목록 전체가 매번 `formatConditionValue`/`senderLabel` 재계산.
- 인라인 화살표 핸들러 `onRetryAgent`/`onAcceptFinalOffer`/`onGiveUp`([NegotiationRoom.tsx:407-409](src/features/negotiation/components/NegotiationRoom.tsx))가 매 렌더 재생성 → 향후 memo를 무력화.

> 📌 참고: 프로젝트 등록 위저드는 이미 방어가 잘 돼 있음 — Context value가 memoize돼 있고([ProjectRegisterContext.tsx:111-130](src/features/client/projects/context/ProjectRegisterContext.tsx)), 스텝별 로컬 state 미러링이라 타이핑이 컨텍스트로 안 번짐. **"이미 잘 된 부분"도 발표 재료**(왜 안 고쳤는지 근거).

## 1-3. 어떻게 측정하나
**(A) React DevTools Profiler — 시각적 확인**
1. React DevTools 확장 → 협상룸 진입
2. Profiler 탭 → ⚙️ **"Highlight updates when components render"** ON → 아무 조작 없이 2.5~10초마다 전체가 번쩍이면 재렌더 확인
3. **Record 30초 방치** → commit 개수 + `NegotiationChatFlow` 렌더 시간(ms) 기록

**(B) `<Profiler>` API — 정량화 (before 수치, 측정 후 제거)**
```tsx

```
→ 협상룸 **30초 무조작 방치** 후 콘솔의 `update` 로그 개수 = "폴링만으로 생긴 재렌더 수".

## 1-4. 개선 방법
- `NegotiationChatFlow` 6모듈로 분해(orchestrator + inputs + panels + 순수 헬퍼) → `MessageItem` 등을 **`React.memo(keyed by messageId)`** 로 감싸 신규 메시지 시점에만 렌더.

# 2. 초기 로딩 속도 / 번들 크기

## 2-1. 개념
- **First Load JS** = 그 라우트를 처음 열 때 받아야 하는 JS 총량. 클수록 TTI(상호작용 가능 시점)가 늦다.
- 줄이는 3대 수단: **코드 스플리팅**(`next/dynamic`, route 분리), **트리 셰이킹**(안 쓰는 코드 제거), **지연 로드**(당장 안 보이는 건 나중에).
- Next.js App Router는 **route 단위로는 자동 스플리팅**하지만, "한 화면 안에서 조건부로만 보이는 트리"는 개발자가 `next/dynamic`으로 쪼개야 함.

## 2-2. 우리 프로젝트 사례 (bundle-analyzer 트리맵으로 확인됨)
- **STOMP가 로그인 번들에까지**: [stomp/client.ts:12](src/features/negotiation/stomp/client.ts)가 `@stomp/stompjs` 정적 import → `reactivateStomp`를 로그인/소셜콜백이 import → 트리맵에서 `chunks/145-*.js` 안 `@stomp/stompjs/bundles/stomp.umd.js` 확인.
- **상세 탭 5개 전부 초기 로드**: [ClientProjectDetail.tsx:7-11,202](src/features/client/myprojects/components/ClientProjectDetail.tsx)가 협상/계약/추천/진행 탭을 전부 정적 import → 기본 "정보"탭만 봐도 다 실림. 트리맵 `app/client/projects/[projectId]/page-*.js` = `ClientProjectDetail.tsx + 11 modules (concatenated)`.
- **`next/dynamic`은 앱 전체에 1곳뿐**(로그인 콜백) → 거의 미사용.
- 📌 큰 초록 블록(`react-dom-client.production.js`)은 React/Next 프레임워크 = **줄일 수 없는 기준선**. 발표 때 "이건 손 못 대는 부분"으로 구분해 말하기.

## 2-3. 어떻게 측정하나
> ⚠️ **정정(실측)**: 우리 프로젝트는 **Next.js 16 + Turbopack**이라 예전의 `next build` "First Load JS" **라우트 표가 출력되지 않는다**(라우트 목록만 나옴). 그래서 baseline은 **빌드 산출물(chunk) 실측**으로 잡는다.

**(A) chunk 실측 — 특정 의존성이 어느 라우트에 실리나 (실제 사용한 방법)**
```bash
npm run build
# 1) 대상 의존성이 들어간 chunk와 크기 찾기 (예: @stomp/stompjs)
grep -rl "@stomp/stompjs\|heartbeatIncoming" .next/static/chunks | while read f; do echo "$(wc -c < "$f")  $f"; done
# 2) 그 chunk를 참조하는 라우트 매니페스트 확인 (특정 라우트가 로드하는지)
grep -rl "<chunk-basename>" .next/server/app | grep -iE "login|negotiation|projects"
```
→ 개선 전/후로 "그 라우트가 chunk를 참조하는가 + chunk 크기"를 비교한다.

**(B) bundle-analyzer — "무엇이 들었나"**
```bash
npm i -D @next/bundle-analyzer
```
`next.config.ts`:
```ts
import type { NextConfig } from "next";
import withBundleAnalyzer from "@next/bundle-analyzer";
const nextConfig: NextConfig = {};
export default withBundleAnalyzer({ enabled: process.env.ANALYZE === "true" })(nextConfig);
```
실행 (Windows PowerShell):
```powershell
$env:ANALYZE="true"; npm run build
```
→ 트리맵 좌상단 `›` 열어 **Gzipped** 모드로 전환(실제 전송 크기). before/after 둘 다 같은 모드로 캡처.

## 2-4. 개선 방법
- 협상룸: 각 `page.tsx`에서 `const NegotiationRoom = dynamic(() => import(...), { ssr: false })`.
- 로그인/콜백: `reactivateStomp`를 정적 import 대신 이벤트 핸들러 안에서 `await import("@/features/negotiation/stomp/client")`.
- 상세 탭: 비기본 탭 4개를 `next/dynamic`으로.
- (전역) `ProjectRegisterComplete`의 `PaymentMethodModal`도 `next/dynamic`.

# 3. 이미지 · 정적 자원 최적화

## 3-1. 개념
- `next/image`: 자동 리사이즈, WebP/AVIF 변환, lazy loading, `width/height`로 **CLS(레이아웃 이동) 방지**.
- `next/font`: 폰트를 셀프 호스팅 + `font-display` 처리해 FOUT/추가 요청 제거.
- 정적 자원 원칙: SVG 아이콘은 인라인 or 스프라이트, 큰 이미지는 포맷/사이즈 최적화, 위쪽에 안 보이는 건 lazy.

## 3-2. 우리 프로젝트 사례 — **"최적화할 이미지가 없다"는 것도 결론** 📌
- 내 파트(등록/목록/상세/협상) 전체에 **`<img>`도 `next/image`도 없음**(grep 확인).
- 아바타 = **CSS 이니셜 원형**([ProjectFreelancerStatus.tsx:58](src/features/client/myprojects/information/components/ProjectFreelancerStatus.tsx), [CandidateCard.tsx:37](src/features/negotiation/components/CandidateCard.tsx)), 파일 아이콘 = **이모지/인라인 SVG**([ProjectInformation.tsx:121](src/features/client/myprojects/information/components/ProjectInformation.tsx)).
- 업로드 파일(PDF/JPG/PNG)은 **이름만 표시**, 이미지로 렌더 안 함.
- 폰트는 이미 **`next/font`(Geist)** 로 셀프 호스팅됨([app/layout.tsx](src/app/layout.tsx)) → 이미 최적.

## 3-3. 발표에서 어떻게 말할까
- "내 파트는 이미지 자산이 거의 없어 **가벼운 벡터/CSS로 처리** → 별도 이미지 최적화 이슈가 애초에 없음"을 **의도된 설계 결정**으로 설명.
- 만약 향후 프로필 사진/포트폴리오 썸네일이 생기면 적용할 규칙만 예고: `next/image` + `sizes` + `priority`(첫 화면만).
- ❓ 확인: 팀원 파트(마이페이지 등)에서 [ClientCompanyInfo.tsx](src/features/client/mypage/components/ClientCompanyInfo.tsx)가 `next/image`를 쓰고 있음 → 그건 팀원 발표 범위.

## 3-4. before / after 기록
| 항목 | 상태 |
|---|---|
| 내 파트 raster 이미지 수 | 0 (측정: grep `<img`/`next/image`) |
| 폰트 최적화 | 이미 `next/font` 적용됨 |
| 결론 | 이미지 최적화 대상 없음 — 설계상 벡터/CSS 사용 |

# 4. 리스트 대량 렌더링

## 4-1. 개념
- 수백~수천 행을 한 번에 DOM에 그리면 렌더/메모리 부담 → **가상화(windowing)**: 화면에 보이는 만큼만 DOM에 유지(`react-window`, `@tanstack/virtual` 등).
- 그 전에 더 싼 방어: **페이지네이션**, **`key` 안정화**, **행 컴포넌트 `React.memo`**, **무거운 계산 `useMemo`**.
- 원칙: **가상화는 비용(복잡도)이 있으니 "진짜 대량"일 때만.** 수십 행이면 memo로 충분.

## 4-2. 우리 프로젝트 사례
- **프로젝트 목록**: [ClientProjects.tsx:83](src/features/client/myprojects/components/ClientProjects.tsx) — **페이지당 10개 페이지네이션** → 대량 아님. 가상화 불필요, 현 구조 적절. 📌
- **협상 메시지 목록**: [NegotiationChatFlow.tsx:127-134](src/features/negotiation/components/NegotiationChatFlow.tsx) — `messages.map(MessageItem)`, **memo 없음**. 협상이 길어지면 메시지가 누적되고, **매 폴링마다 전체 재계산**(1번 문제와 연결). → **여기가 진짜 리스트 이슈**.
- 추천 후보 목록 [RecommendedCandidates.tsx](src/features/client/myprojects/recommendation/components/RecommendedCandidates.tsx)도 소량이라 memo 수준이면 충분.

## 4-3. 어떻게 측정하나
- **React Profiler**로 메시지 목록이 몇 개까지 커지는지 + 매 갱신 시 몇 개 행이 리렌더되는지 기록.
- **Performance 패널**로 메시지 100개 가정 시 scripting 시간 측정(협상 목업 데이터로).
- 판단 기준: 행 수가 **수백 이상 + 스크롤 렉**이면 가상화, 아니면 **memo로 끝**.

## 4-4. 개선 방법 (우선순위)
1. `MessageItem`을 `React.memo`로 (즉효, 저비용) — 1번 개선과 동일 작업.
2. 행 내부 포맷 계산을 `useMemo` 또는 상위에서 1회 계산.
3. (조건부) 메시지가 수백 건 이상 흔하면 그때 `react-window` 도입 검토 — **지금은 과설계 가능성**, 측정 후 결정.

## 4-5. before / after 기록
| 지표 | before | after | 비고 |
|---|---|---|---|
| 메시지 N건일 때 1회 갱신 리렌더 행 수 | 전체(N) | 신규만 | memo 전/후 |
| 목록 화면 스크롤 렉 체감 | ? | | Performance 패널 |
| 가상화 도입 여부 | — | | 측정 결과에 따라 |

> 🎤 "리스트 최적화 = 무조건 가상화가 아니다. 목록은 이미 10개 페이지네이션이라 memo면 충분했고, 진짜 병목이던 협상 메시지 목록만 골라 최적화했다 — 측정으로 과설계를 피한 사례."

# 6. 채팅·고객문의(support) 파트 — 렌더링 전략 + 실측 결론

> 이 파트는 "무겁게 고친 것"보다 **"측정해서 안 고친 근거"와 "렌더링 전략 전환"**이 발표 포인트다.

## 6-1. 렌더링 전략: 공개 페이지만 SSG로 (SSR/ISR/SSG 판단) 🎤
- 문제: `/support` 허브는 **공개**(sitemap 노출)인데 `getServerCurrentUser()`(요청 쿠키 `headers()`)를 써서 **매 요청 SSR(dynamic)**. 본문은 하드코딩 카드 2개라 사용자 정보가 필요한 건 헤더뿐.
- 판단: **ISR이 아니라 SSG**. 이 페이지는 갱신할 외부 데이터가 0이라 `revalidate`(ISR)는 동일 HTML을 타이머로 재생성만 함 → 빌드 1회 생성(SSG)이 정답.
- 조치: `getServerCurrentUser` 제거 + `export const dynamic = "force-static"`. 인증·사용자별 데이터가 필요한 `/support/chatbot`, `/support/inquiries/*`는 dynamic 유지(robots도 이미 disallow).
- before/after: `npm run build` 라우트표에서 `/support` **`ƒ`(Dynamic) → `○`(Static)** 전환 확인(캡처: 빌드 로그). 효과 = 매 진입 `/auth/me` 서버 왕복 제거로 TTFB 개선 + 공개 페이지 SEO(메타) 확보.
- 트레이드오프(발표에서 정직하게): SSG는 모든 사용자에게 같은 HTML → 정적 HTML은 게스트 헤더로 나감. 6-2로 보완.

## 6-2. SSG 부작용(헤더 깜빡임)과 스켈레톤 보완 🎤
- 원인: 정적 HTML=게스트 헤더 → 로그인 유저가 하드진입 시 클라 조회 후 '게스트→로그인'으로 **틀린 상태를 잠깐 노출**.
- 조치: 공용 `Header`에 `isLoading && !user`면 `HeaderSkeleton`(중립 placeholder) 반환. auth 훅은 이미 `isLoading` 제공 → **로직 무변경, 헤더 진입점 1곳만 수정**.
- 좋은 성질: SSR 페이지는 `initialUser`로 `isLoading=false` → 스켈레톤 미노출. 실효 영향이 **SSG 페이지에 한정**돼 전역 리스크 낮음. "틀린 상태 노출 → 중립 placeholder"로 체감 깜빡임 제거.

## 6-3. 번들 실측 — "고칠 게 없다"는 결론도 근거로 📌
- `ANALYZE=true npm run build` + 빌드 청크 실측(gzip):
  - react-dom(프레임워크) 69.7KB / Next 런타임 41.3·38.6KB — 불가피
  - **`@stomp/stompjs` 6.6KB(gzip), `/chat` 라우트에만 국한** — 공유 번들 미포함(헤더의 `useUnreadChatCount`는 REST만 참조). 코드분할 이미 양호
  - **lucide-react**: named import 3곳뿐 + Next 기본 `optimizePackageImports`로 per-icon 트리셰이킹 → 추가 설정 불필요
- 결론: 코드분할/의존성 제거 이득 없음 → `next.config`는 하이진(`poweredByHeader:false`, `productionBrowserSourceMaps:false`)만. **"측정해서 안 했다"의 대표 사례.**

## 6-4. 이미지 — 대상은 있으나 보류(호스트 미확정) ❓
- 채팅 아바타(`Chat.tsx`)가 `next/image`에 `unoptimized`. 최적화 대상은 맞으나 실제 이미지 호스트(S3/CDN) 미확정이라 `remotePatterns` 추측 금지 → `next.config`에 TODO 주석만. 호스트 확정 시 `unoptimized` 제거 + 등록. (32~40px라 이득은 작음)
