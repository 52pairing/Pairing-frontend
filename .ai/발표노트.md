# 발표 노트 (러닝 기록용)

> 이 문서는 **발표 대본이 아니라 "재료 창고"** 입니다. 발표 목차 그대로 칸을 만들어 두었으니, 개발/대화 중 쓸 만한 걸 해당 칸에 던져 넣으세요.
> 내 담당 파트: **프로젝트 등록 / 목록 / 상세(정보·협상)**. 로그인·매칭·마이페이지·메인은 팀원 파트.
>
> **태그**: 발표에 실제 쓸 것 `🎤` · 참고 `📌` · 확인 필요 `❓` · 내가 채울 슬롯 `⬜`
> `📌`로 시작하는 항목은 **실제 코드에서 확인된 사실**이라 바로 써도 됩니다.

# 1. 프론트엔드 기능

## 1-1. 구현한 화면·기능 목록
📌 실제 라우트/컴포넌트 기준:

- **프로젝트 등록 위저드** (`/client/projects/new/*`, 7단계 · 단계마다 별도 라우트)
  - 안내·약관 동의(intro) → 기본 정보(basic) → 모집 역할(roles) → 상세 내용(details) → 검토(review) → 최종 확인 + **내용 사전점검**(confirm) → 등록 완료 + 결제수단(complete)
- **프로젝트 목록** (`/client/projects`)
  - 탭별(등록 완료 / 모집중 / 협상중 / 진행중 / 완료 대기 / 종료 등) 카드 리스트 + 페이지네이션 + 탭별 건수 배지
- **프로젝트 상세** (`/client/projects/[projectId]`)
  - 탭: 프로젝트 정보 / 추천 후보 / 협상 / 계약 / 진행 현황 — **내 담당: 정보 탭 + 협상**
  - 정보 탭: 메타(예산·기간·역할·스킬·근무조건) + 첨부파일 다운로드 + **프리랜서 매칭 요청 현황**
- **협상룸** (`/client/projects/[projectId]/negotiation/[negotiationId]`)
  - **AI 대리인 실시간 협상**(STOMP), 조건별(금액·기간·근무방식 등) 제안/수락, 최종 절충, 결렬·완료 결과 카드

⬜ 위 목록 중 발표에서 특히 부각할 화면 표시하기

## 1-2. 사용자 흐름상 각 화면의 역할
📌 흐름: **등록(공급 생성) → 목록(관리 허브) → 상세(단일 프로젝트 관제) → 협상(체결 직전 조율)**

- 등록 위저드: 클라이언트가 프로젝트를 "생성"하는 진입점. 단계별로 정보 수집.
- 목록: 내가 올린 프로젝트를 상태별로 관리하는 대시보드. 다음 액션(결제/완료/상세)으로 분기.
- 상세-정보: 한 프로젝트의 현재 상태와 지원/매칭 현황을 한눈에.
- 협상룸: 특정 후보와 조건을 확정 직전까지 좁히는 실시간 공간.

⬜ 각 화면 전환의 "왜"를 한 줄씩 (사용자가 왜 이 순서로 움직이나)

## 1-3. 사용자 경험을 위해 특별히 신경 쓴 부분
📌 코드로 확인되는 것:
- **등록 위저드 상태 보존**: 단계 이동·새로고침에도 폼 유지 (Context를 layout에 두고 sessionStorage 동기화)
- **제출 전 내용 사전점검**: 개인정보(연락처·이메일 등) 노출·반복 문구를 **제출 전에 경고** (외부 전송 없이 로컬 검사)
- **협상 실시간성 + 중복 제출 방지**: STOMP 즉시 반영, 요청 중 버튼 비활성화
- **로딩/에러/빈 상태 처리**: 목록·상세·협상 모두 3상태 렌더
- **접근성**: 단일 `h1`, `label`/`aria-*`, `role="alert"` 등 (분석상 양호)
- **테마 FOUC 방지**: 초기 스크립트로 첫 페인트부터 올바른 다크/라이트

⬜ 이 중 "내가 의도적으로 공들인 것" 1~2개 골라 스토리로

## 1-4. 구현하려 했으나 제외한 화면·기능과 그 이유
- ❓⬜ 실제 제외/축소한 항목 — **본인 경험으로 채우기**
- 📌 힌트(연기 결정 근거 있음): 등록 **사전점검을 임베딩/AI 기반이 아닌 규칙 기반 1단계로 한정**, 임베딩 유사도 방식은 후속 과제로 분리 → 이건 4-4(AI 안 쓴 판단)와 연결

> 🎤 훅 후보: "화면을 다 만드는 게 아니라, **지금 사용자에게 필요한 만큼만** 만들고 나머지는 근거를 남겨 미뤘다."

# 2. AI 기능

> ⚠️ 실제 AI 모델은 **백엔드에서 동작**하고, FE는 입력 수집·실시간 수신·결과 렌더 담당. 모델/제공자 이름은 **추측하지 말고 백엔드 확인 후** 기입.

## 2-1. 어떤 문제를 AI로 풀었는가 (기능 단위)
📌 확인된 AI 기능:
- **AI 대리인 협상**: 클라이언트↔프리랜서가 직접 흥정하는 대신, **AI 대리인이 조건(금액·기간 등)을 자동으로 절충**. 사용자는 하한/상한(floor)만 정하고 나머지는 AI가 진행.
- ❓ **후보 추천**("추천 후보" 탭): 매칭 추천이 AI/규칙 중 무엇인지 **확인 필요** (백엔드 로직).

⬜ 각 기능이 "해결한 사용자 고통" 한 줄

## 2-2. 사용한 모델·API·라이브러리와 선택 근거
- 📌 FE 측: **`@stomp/stompjs`** (STOMP over WebSocket) — AI 협상 이벤트 실시간 수신 + 폴링 병행(2.5초/10초)
- ❓ 백엔드 AI 모델/API: ⬜ (제공자·모델명·호출 방식 — 백엔드 담당 확인)
- ⬜ 선택 근거: 왜 실시간(WebSocket)인가 / 왜 폴링 병행인가

## 2-3. AI 기능의 입력과 출력, 사용자에게 보이는 형태
📌 협상 기준:
- **입력**: 사용자가 설정한 조건 하한/상한(예: 최소 단가, 최대 기간), 협상 시작
- **출력**: AI 대리인의 조건별 제안 메시지, 최종 절충안, 합의/결렬 결과
- **보이는 형태**: 협상 채팅 타임라인 + 조건 배지 + "AI 대리인이 협상 중…" 상태 표시 + 결과 카드(완료/결렬)

⬜ 실제 화면 캡처 위치 남기기

## 2-4. AI 기능이 서비스 가치에 실제로 기여한 지점
- 📌 사람이 직접 밀당하는 마찰 제거 → 체결까지의 시간·감정 비용 절감
- 📌 하한(floor) 보호 안에서 자동 합의 → 손해 보는 조건 방지
- ⬜ 정량 근거 있으면(체결률/소요시간 등) 여기에

## 2-5. AI를 쓰지 않기로 결정한 부분과 그 판단
- 📌🎤 **등록 사전점검을 규칙 기반으로 결정**: 개인정보 탐지는 정규식, 반복 문구는 문자열 유사도(bigram Dice)로 처리. 임베딩/LLM을 **안 쓴 이유** — ① 프라이버시(입력을 외부로 안 보냄) ② 비용·지연 없음 ③ 설명 가능(왜 걸렸는지 명확). 임베딩 유사도 방식은 **후속 spike로 분리**.
- ⬜ 그 외 "AI 대신 규칙/서버 로직" 선택한 지점

> 🎤 훅 후보: "**AI를 쓸 곳과 안 쓸 곳을 나눈 기준**이 있었다 — 협상처럼 판단이 필요한 곳엔 AI, 개인정보 점검처럼 정확·투명·저비용이 중요한 곳엔 규칙."

# 3. 프론트엔드-백엔드 협업에서 겪은 문제

## 3-1. API 계약 합의
- ⬜ **스펙 확정 시점·주체**: 누가 언제 확정했나 (본인 경험)
- 📌 **명세 문서화**: `.ai/API.md`에 프론트에서 실제 쓰는 요청·응답·에러를 기록하는 방식 유지
- ⬜ **변경 통보 절차와 준수 여부**: 스펙 바뀔 때 어떻게 공유됐나 / 잘 지켜졌나
- 📌 **명세 불일치 재작업 흔적**: 응답 타입에 **미사용 필드 다수**(스펙 변화의 잔재), 필드 존재 여부를 FE가 방어(`?? 원문`)하는 패턴 다수 → 계약이 유동적이었음을 시사
  - ⬜ 실제로 재작업했던 구체 사례 하나 (어떤 필드/응답이 바뀌어 화면이 깨졌나)

## 3-2. 화면 단위 데이터 책임 설계 — "서버는 코드만, 조립은 FE가" (✅ 코드 검증)

**실제로 벌어지는 일** — [ClientProjectDetail.tsx:71-81](../src/features/client/myprojects/components/ClientProjectDetail.tsx):
```
const [detail, jobRoles, skills, workConditions] = await Promise.all([
  getClientProjectDetail(projectId),  // ① 프로젝트 본문 — 단, "코드"로 옴
  getProjectJobRoles(),               // ② 직무 코드→라벨 사전
  getProjectSkills(),                 // ③ 스킬 코드→라벨 사전
  getProjectWorkConditions(),         // ④ 근무방식/형태 코드→라벨 사전
]);
setJobRoleLabels(Object.fromEntries(jobRoles.map((i) => [i.code, i.label]))); // FE가 직접 join
```
- ①상세는 직무·스킬·근무조건을 **코드값**(`"BACKEND"`)으로만 내려줌 → 라벨("백엔드")은 안 옴 → FE가 사전 ②③④를 따로 받아 **코드→라벨 join을 직접**(78-81줄).
- 자식 [ProjectFreelancerStatus.tsx:35](../src/features/client/myprojects/information/components/ProjectFreelancerStatus.tsx)가 `getProjectMatchingRequests`를 **독립 1개 더** → **정보 탭 1개 = 총 5개 호출**.

**구체적 부담 3가지 (✅ 검증)**
1. **화면 조립을 서버 아닌 FE가 함**: 서버가 라벨까지 붙였으면 1호출로 끝날 걸, "코드만" 계약이라 사전 3개 받아 join.
2. **정적 데이터를 매번 재요청**: 직무/스킬/근무조건은 거의 안 바뀌는 참조 데이터인데 진입마다 `Promise.all`에 포함(캐시 없음).
3. **에러 all-or-nothing**: 4개가 한 `try/catch`(70-83줄) → 사전 하나만 실패해도 상세 전체가 에러 화면.

- ⬜ **판단**: 화면 전용 API(BFF)를 만들지 팀에서 논의했는지 / 왜 안 만들었는지 (본인 경험)

> 🎤 "프로젝트 정보 화면 하나를 그리려고 프론트에서 API를 5번 호출했다. 서버가 코드만 주니 **라벨 변환(조립)을 프론트가 직접** 해야 했다 — 어디까지 서버가 조립할지가 협업의 핵심 논점."

## 3-3. 도메인 용어·상태 기준 정렬 — "같은 코드, 다른 말" (✅ 코드 검증)

**뿌리는 3-2와 같음**: 백엔드가 상태도 **코드**(`COMPLETION_PENDING`)로만 주고 **공용 라벨 소스가 없어** 화면마다 자기 `STATUS_LABEL` 맵을 따로 선언 → 어긋남. **실측 맵 4개**:

| 코드 | ①프로젝트 | ②매칭요청 | ③계약/진행 | ④매칭상세 |
|---|---|---|---|---|
| `COMPLETION_PENDING` | 완료 대기 | 완료 대기 | **정산 대기** ⚠️ | 완료 대기 |
| `IN_PROGRESS` | 진행중 | 진행중 | 진행중 | **진행 중** ⚠️ |
| `NEGOTIATING` | 협상중 | 협상중 | — | **협상 중** ⚠️ |
| 종료 개념 | `CLOSED`=**종료** | CLOSED=종료 | `COMPLETED`=**완료** ⚠️ | CLOSED=종료 |

출처: ①[projectDisplay.ts](../src/features/client/myprojects/utils/projectDisplay.ts) ②[ProjectFreelancerStatus.tsx:10](../src/features/client/myprojects/information/components/ProjectFreelancerStatus.tsx) ③[ProjectProgress.tsx:13](../src/features/client/myprojects/progress/components/ProjectProgress.tsx) ④[ClientMatchingRequestDetail.tsx:9](../src/features/matching/components/ClientMatchingRequestDetail.tsx)

**확인된 불일치 3종류 (✅ 검증)**
1. **의미가 갈림**(제일 심각): `COMPLETION_PENDING` = 프로젝트 화면 "완료 대기" vs 계약/진행 화면 **"정산 대기"**. 같은 프로젝트를 탭만 바꿔도 다른 말.
2. **"완료·종료" 뒤엉킴**(발표 예시와 정확히 일치): 프로젝트 종료 = `CLOSED`="종료" / 계약 종료 = `COMPLETED`="완료" → "완료·종료·완료 대기·정산 대기"가 도메인마다 다르게 배치.
3. **표기 흔들림**: `NEGOTIATING`·`IN_PROGRESS`가 "협상중/진행중"(붙임) vs "협상 중/진행 중"(띄움).
- 보너스: ②맵은 `PENDING`·`REQUESTED`·`REQUEST_PENDING` **세 코드를 모두 "요청 대기"**로 매핑 → 같은 개념에 코드가 여러 개거나 FE가 방어한 흔적 → **3-1(API 계약 불안정)과 연결**.

- ⬜ **용어집·상태 정의 정리 시점·방법**: 실제 답 → 이번 리팩터링에서 **프로젝트 상태 맵 중복 2곳을 `projectDisplay.ts` 하나로 정본화**, 의미가 다른 매칭·계약 맵은 **의도적으로 병합 안 함**. "①은 정본화 완료 / 도메인 간 드리프트는 남은 과제"로 발표하면 정확.

> 🎤 "`COMPLETION_PENDING` 하나가 화면 따라 '완료 대기'도 '정산 대기'도 됐다. 상태 라벨이 네 군데에 흩어져 도메인마다 제각각 정의돼 있었다."

> 🎤 **두 섹션 연결**: "백엔드가 '코드'만 내려주는 계약이었다. 그래서 화면 조립(라벨 join)도, 상태 해석(라벨 맵)도 프론트가 떠안았고 — 조립은 화면당 5개 호출로, 해석은 도메인마다 어긋난 라벨로 드러났다."
